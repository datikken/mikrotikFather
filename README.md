# OpenVPN на VDS

Docker Compose-конфигурация OpenVPN-сервера для будущего соединения двух LAN через VDS. Серверный туннель работает в режиме TUN по UDP; LAN-маршруты добавляются отдельно для каждого клиентского сертификата. Сервер не включает NAT для трафика между клиентами.

## Подготовка VDS

На VDS установите Docker Engine с плагином Docker Compose v2. В панели хостинга разрешите входящий **UDP 1194**. Если на VDS используется firewall, разрешите этот порт там тоже. Не открывайте UDP 7777 на VDS: это порт обмена плат внутри VPN, а не порт VPN-сервера.

Передайте файлы проекта на VDS и запускайте команды из корня проекта. Go CLI запускается внутри отдельного контейнера и управляет Docker Compose через Docker socket:

```text
docker compose run --build --rm -it cli create <публичный-IPv4-или-DNS>
docker compose run --rm cli status
```

Например, укажите публичный адрес или DNS-имя VDS:

```text
docker compose run --build --rm -it cli create vpn.example.com
```

При создании CA команда интерактивно попросит ввести и подтвердить пароль. Позже Easy-RSA попросит этот же пароль для подписи серверного сертификата и создания списка отозванных сертификатов (CRL). Флаги `-it` нужны, чтобы терминал передавал ввод через CLI-контейнер в Easy-RSA. Сохраните пароль отдельно. Если при первой попытке вы ввели его неверно, повторите `docker compose run --build --rm -it cli create <публичный-IPv4-или-DNS>` и введите пароль CA правильно: утилита продолжит незавершённую подпись, не удаляя созданную PKI. Команды `init`, `up`, `down`, `restart`, `status` и `logs` запускаются аналогично, например `docker compose run --rm cli down`. Остановка удаляет OpenVPN-контейнер и его Docker-сеть, но сохраняет PKI и настройки в `data/`.

Если Easy-RSA при первом запуске уже создал CA, но серверный сертификат не подписался из-за неверного пароля CA, повторите `create` с правильным паролем. Для ручного восстановления существующего запроса без пересоздания CA:

```text
docker compose run --rm -it openvpn easyrsa sign-req server <имя-сервера-из-лога>
docker compose run --rm -it openvpn easyrsa gen-crl
docker compose up -d openvpn
```

На обоих запросах введите пароль CA. Не удаляйте `data/`: там находится CA и уже созданные ключи.

Контейнер CLI монтирует Docker socket хоста; доступ к нему фактически даёт полный контроль над Docker и root-доступ к VDS. Запускайте его только из доверенной копии этого проекта и не публикуйте Docker socket по сети.

Если OpenVPN-контейнер перезапускается с ошибкой `Unrecognized option ... data-ciphers (2.4.9)`, обновите проект и повторно выполните `docker compose run --build --rm -it cli create <публичный-IPv4-или-DNS>`. CLI уберёт несовместимые с OpenVPN 2.4 директивы из существующего конфига и пересоздаст контейнер, сохранив PKI. Предупреждения образа про IPv6 forwarding не относятся к этой IPv4-схеме; для неё важнее, чтобы OpenVPN запустился и был доступен UDP 1194.

## Панель OpenVPN Admin

Панель `ovpn-admin` управляет сертификатами, поэтому она не публикуется напрямую. Nginx принимает HTTP на порту 80 и перенаправляет на HTTPS 443; панель требует Basic Auth. Для доступа по IP используется самоподписанный сертификат: браузер покажет предупреждение о доверии сертификату, пока вы не установите его в доверенные.

Сначала создайте каталог для файлов защиты:

```text
mkdir -p nginx/auth nginx/certs
```

Создайте сертификат с IP-адресом в Subject Alternative Name:

```text
docker run --rm -v "$PWD/nginx/certs:/certs" alpine/openssl req -x509 -nodes -days 365 -newkey rsa:3072 -keyout /certs/server.key -out /certs/server.crt -subj "/CN=185.219.43.239" -addext "subjectAltName=IP:185.219.43.239"
```

Создайте пользователя Basic Auth. Команда запросит пароль интерактивно; не указывайте пароль аргументом команды:

```text
docker run --rm -it -v "$PWD/nginx/auth:/auth" httpd:2.4-alpine htpasswd -cB /auth/.htpasswd admin
```

Если OpenVPN уже был создан до добавления панели, обновите его конфигурацию, чтобы включить локальный management-интерфейс. Команда сохраняет существующую PKI, но пересоздаёт OpenVPN-контейнер:

```text
docker compose run --build --rm -it cli create 185.219.43.239
```

Для нового сервера этот шаг уже выполняется обычной командой `create`. Ограничьте доступ к портам TCP 80 и 443 в firewall VDS. Запустите OpenVPN и защищённую панель:

```text
docker compose up -d openvpn
docker compose --profile admin up -d openvpn-admin nginx
```

Откройте `https://185.219.43.239` и войдите с заданными Basic Auth учётными данными. HTTP `http://185.219.43.239` перенаправит на HTTPS. Если после обновления `openvpn.conf` панель не показывает состояние, выполните `docker compose restart openvpn openvpn-admin nginx`.

OpenVPN management слушает только `127.0.0.1:8989` внутри общей сетевой области OpenVPN и контейнера панели; этот порт не публикуется на VDS. Порт 8080 панели также доступен только во внутренней Docker-сети за Nginx. Не открывайте их в firewall. Сам `ovpn-admin` предупреждает, что приложение не проектировалось с упором на безопасность; Basic Auth и TLS защищают веб-доступ, но для более строгой изоляции ограничьте вход на 80/443 до доверенных IP или используйте доступ только через VPN.

Панель предназначена здесь для просмотра подключений. При зашифрованном CA-ключе (как в текущей конфигурации сервера) используйте Go CLI для выпуска и отзыва сертификатов; операции сертификатов из `ovpn-admin` могут не выполниться, так как интерфейс не запрашивает пароль CA интерактивно.

### Запуск CLI на VDS вне контейнера

Чтобы запускать `openvpnctl` непосредственно в Ubuntu, соберите Linux-бинарник. Если Go установлен на VDS:

```text
go build -o openvpnctl ./src
chmod +x openvpnctl
./openvpnctl up
```

Если Go на VDS не установлен, соберите бинарник через временный Go-контейнер; само управление после сборки выполняется на хосте:

```text
docker run --rm -v "$PWD:/src" -w /src golang:1.24-alpine go build -o openvpnctl ./src
chmod +x openvpnctl
./openvpnctl up
```

Запускайте команды из корня проекта, где находится `compose.yaml`. На VDS должны быть установлены Docker CLI и Compose plugin v2. Для остановки используйте `./openvpnctl down`; для справки — `./openvpnctl`.

## Добавление клиента позже

Создайте отдельный сертификат и укажите LAN, которая будет находиться за этим клиентом:

```text
docker compose run --rm cli add-client radio 192.168.88.0/24
docker compose run --rm cli add-client module 192.168.55.0/24
```

Команда создаёт профиль `clients/<имя>.ovpn`, запись `iroute` для клиента, маршрут в конфигурации сервера и перезапускает сервер, если он запущен. Для каждого клиента задавайте его собственную, непересекающуюся LAN-подсеть. Имя клиента должно быть уникальным. Профиль содержит закрытый ключ и создаётся с правами `0600`; передавайте его только по защищённому каналу.

Для подготовленной в задании пары MikroTik используйте одну команду:

```text
docker compose run --rm cli add-mikrotik-pair
```

Она выпускает сертификаты и профили `clients/mikrotik-a.ovpn` и `clients/mikrotik-b.ovpn`, настраивает маршруты между ними и перезапускает сервер. В этом развертывании `mikrotik-a` (Radio) использует LAN `192.168.88.0/24`, а `mikrotik-b` (Module) — `192.168.55.0/24`. Профили используют UDP, TUN, AES-256-CBC, SHA256 и `tls-auth`, совместимые с импортом OVPN-профиля в RouterOS. Для OVPN/UDP требуется RouterOS 7.17 или новее. Обратите внимание: команда `add-mikrotik-pair` в исходном коде по умолчанию задает для Radio сеть `192.168.66.0/24`; для создания такой пары с нуля этот адрес нужно согласовать с фактической LAN MikroTik A.

Команды управления:

```text
docker compose run --rm cli
docker compose run --rm cli status
docker compose run --rm cli logs
docker compose run --rm cli restart
docker compose run --rm cli down
docker compose run --rm cli up
```

Запуск CLI без аргументов выводит справку со списком доступных команд.

## Схема этого развертывания

```text
192.168.88.0/24 (Radio) <-- OpenVPN TUN/UDP --> VDS <-- OpenVPN TUN/UDP --> 192.168.55.0/24 (Module)
```

OpenVPN использует UDP 1194, TUN-подсеть `10.8.0.0/24` и AES-256-CBC с HMAC-SHA256 для совместимости с RouterOS и серверным образом OpenVPN 2.4.9. Отключена отправка клиентам маршрута по умолчанию и DNS-настроек. Включена маршрутизация между VPN-клиентами. UDP 7777 не публикуется в интернет.

После копирования каждого профиля на MikroTik импортируйте его через меню **Interfaces → OVPN Client → Import OVPN Configuration** (либо соответствующую команду `/interface/ovpn-client/import-ovpn-configuration`). Укажите имя пользователя клиента и любой непустой пароль: сервер настроен на аутентификацию сертификатом и не использует парольную аутентификацию. Затем проверьте параметры созданного OVPN-интерфейса: `protocol=udp`, `mode=ip`, `cipher=aes256-cbc`, `auth=sha256`.

### Импорт профиля в RouterOS 7

1. На Radio-роутер загрузите `clients/mikrotik-a.ovpn`, на Module-роутер — `clients/mikrotik-b.ovpn`. В WinBox откройте **Files** и перетащите нужный файл на роутер.
2. Откройте **Terminal** и импортируйте профиль:

   Для Radio:

   ```routeros
   /interface/ovpn-client/import-ovpn-configuration file-name=mikrotik-a.ovpn
   ```

   Для Module:

   ```routeros
   /interface/ovpn-client/import-ovpn-configuration file-name=mikrotik-b.ovpn
   ```

3. Если RouterOS запросит учётные данные, задайте имя пользователя и непустой пароль. Сервер использует сертификатную аутентификацию; пароль CA — отдельный и не используется для VPN-подключения.
4. Проверьте созданный интерфейс и состояние подключения:

   ```routeros
   /interface/ovpn-client/print detail
   ```

   Убедитесь, что используются UDP и IP/TUN-режим, а интерфейс подключён. Для OVPN по UDP требуется RouterOS 7.17 или новее.

Файл `.ovpn` содержит закрытый ключ клиента: передавайте его только на соответствующий роутер и не публикуйте.

При подключении сервер отправляет каждому MikroTik маршрут к удалённой LAN. На обоих роутерах проверьте, что он появился в таблице маршрутизации, firewall разрешает `forward` для UDP 7777 между `192.168.88.0/24` и `192.168.55.0/24`, а masquerade не подменяет адреса этого трафика. Серверный маршрут и `iroute` на VDS сохраняют исходные IP-адреса; NAT для межсетевого трафика не включается. RTT менее 250 мс зависит от географии, маршрута и нагрузки VDS, поэтому его нужно измерить после подключения.

## Данные и резервное копирование

Каталог `data/` содержит конфигурацию OpenVPN, CA, закрытые ключи и клиентские сертификаты. Каталог `clients/` содержит готовые профили с закрытыми ключами. Оба каталога исключены из Git — храните их резервные копии в защищённом месте. Не публикуйте их и не отправляйте в систему контроля версий.

`docker compose run --rm cli init <публичный-IPv4-или-DNS>` можно повторить: существующие конфигурация и PKI не перезаписываются. Для изменения публичного адреса отредактируйте `remote` в профилях клиентов после их создания и перезапустите соответствующий клиент.

## Примечание по фактической настройке MikroTik

Профиль `.ovpn` настраивает VPN-клиент, но не меняет IP-адрес LAN, DHCP-пул или адрес `bridge` на самом MikroTik. Команда `add-mikrotik-pair` задаёт сети маршрутизации заранее: `192.168.66.0/24` для `mikrotik-a` и `192.168.55.0/24` для `mikrotik-b`. Она не обнаруживает реальные LAN-подсети роутеров. Перед генерацией профилей проверьте на обоих устройствах `/ip/address/print` и убедитесь, что LAN-подсети различаются и не пересекаются.

В этой установке MikroTik A изначально использовал `192.168.88.0/24`, а MikroTik B — ту же стандартную подсеть. Для сохранения LAN A серверный маршрут и `iroute` были приведены к `192.168.88.0/24`, а LAN B перенесена на `192.168.55.0/24`. После изменений маршрут с B к `192.168.88.0/24` и обратный маршрут с A к `192.168.55.0/24` стали активными.

Если маршрут не появляется, проверьте логи OpenVPN. Сообщение `Could not access file '/etc/openvpn/ccd/<имя-клиента>': Permission denied` означает, что сервер не может прочитать CCD и не отправит заданный в нём `push "route ..."`. После исправления доступа в этой установке сервер прочитал CCD и отправил B маршрут `192.168.88.0/24`. Сообщения `Bad compression stub decompression header byte` указывают на несовместимость настройки сжатия: в этой конфигурации обнаруживалась устаревшая директива `comp-lzo no`; удалите её из серверного `data/openvpn.conf`, перезапустите OpenVPN и переподключите клиентов. Не считайте один только флаг `R` доказательством исправной передачи трафика — проверяйте маршруты и связь ping между LAN.
